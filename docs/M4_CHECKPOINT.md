## 已定位的接入点

- [`main.py` 的 `run_activity`](../plugin/astrbot_plugin_bili_activity/main.py#L1611) 已负责记录生活选择、检查项目门控、领取目标和写入运行账本。DSH 适合接在 `claim_goal` 之后，由同一运行流程选择执行方式。文件任务分支应与后面的手机在线检查分开。
- [`LifeState.update_goal`](../plugin/astrbot_plugin_bili_activity/life.py#L269) 已支持 JSON 检查点，并校验目标的运行归属。启动恢复会把运行中目标置回暂停。应保留原目标状态，先核实如何合并独立的 DSH 检查点字段，避免覆盖原有研究进度。
- [`Workshop.revise`](../plugin/astrbot_plugin_bili_activity/workshop.py#L220) 按 `request_key` 和预期版本保护重复写入。原版运行结束还会记录来源经历并按现有策略将摘要交给记忆队列。M4 的产物引用和记忆回写应复用这些入口。

## 恢复后先做的验证

1. 用临时 SQLite 库和本机模拟 DSH，从一个原版生活选择及其已领取目标开始。验证投递前能保存稳定任务标识、DSH 会话与请求标识，以及预期产物路径。
2. 在投递后、写回前模拟重启。优先按已保存的会话查询 DSH。结果无法确认时将 DSH 检查点标记为 `needs_review`，禁止自动重投。检查点状态与上游目标状态分别保存。
3. 核验产物和来源后，使用同一请求键写回目标与原有作品或记忆入口。重复恢复两次，确认只有一次有效写回。再用时钟验证跨越北京时间 04:00 时，任务标识和原归属仍一致。

现有开发实例的 QQ 入口只开放 `/dsh ping`。自主付费任务仍处于关闭状态。先通过无付费的生命周期测试，再安排一次受控联调。
